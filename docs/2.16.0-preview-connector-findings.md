# OPC PLC 2.16.0 preview – findings from Azure IoT Operations OPC UA connector E2E

Source: the Azure IoT Operations OPC UA connector E2E suite. We ran it against
`2.16.0-preview.1` and then against `2.16.0-preview.4`, using the Docker image and the
Helm chart `microsoft-opc-plc:1.2.25`. The baseline is `2.15.x`, where all of these
scenarios pass.

## Summary

| # | Area | preview.1 | preview.4 | Owner |

## Details

### 1. UpdateCertificate (fixed in preview.4)
- **preview.1:** after a GDS push, `UpdateCertificate` returned `Bad` and the server kept
  presenting its original self-signed certificate.
- **preview.4:** the pushed certificate is applied. GDS-related E2E failures dropped from 9 to 5.

The server now also validates the issuer chain during `UpdateCertificate`. If the issuer is not
yet in the trust list, it returns `BadCertificateChainIncomplete`. This is spec-aligned
(Part 12, 7.10.4). The connector is fixing its push order: trust list first, then certificate.

### 2. CreateSigningRequest / pending key storage (preview.4)
- In preview.4, `CreateSigningRequest` persisted the pending private key in a separate Kubernetes
  Secret named like `microsoft-opc-plc-own-<app>-pending-<own-name-hash>-<scope-hash>`.
- The Role `opcplc-secrets-role` in Helm chart `1.2.25` has these limits:
  - It grants no `create` verb on `secrets`.
  - It pins `resourceNames` to the pre-existing secret names.
- As a result, the API server returns **403 Forbidden**. The client only sees a generic `Bad`,
  with no hint about the real cause.

**Follow-up:** PLC now logs Kubernetes 403 read/write failures and returns `BadUserAccessDenied`.
Pending-key data is now stored in reserved entries in the existing own-certificate Secret, rather
than creating a second Secret. This removes the need for the chart to grant `create` on arbitrary
Secret names. The existing Secret must remain readable and updateable by the PLC. Pending keys are
retained while `UpdateCertificate` stages the signed certificate and consumed during successful
`ApplyChanges` activation. Unused keys expire after 24 hours in all three store modes and are removed
on the next pending-key access. Store reopening, repeat saves of the same key, and activation rollback
do not extend the lifetime; expired claimed keys cannot be restored.

Local regressions cover all three stores, restart recovery, expiry at the 24-hour boundary,
rollback age preservation, concurrent Secret mutations, and preservation of the active key.
The GDS wire regression also verifies that a simulated Kubernetes 403 during CSR persistence is
reported as `BadUserAccessDenied`, and that retrying after permission recovery succeeds.
This uses an in-memory Kubernetes client; live Helm chart RBAC and the original AIO connector
E2E suite still need deployment validation.

### A. SubPath mixed-validity write returns 5 errors instead of 4
- **Scenario:** a single Write request with several SubPath nodes. Some values are valid and
  some are invalid (wrong type or out of range).
- **Observed (preview.1):** 5 bad per-item results. On 2.15.x it was 4: one value that used to
  succeed is now rejected.
- **Status:** still needs an AIO connector rerun with the original mixed-validity request payload.
  Local relative-path tests cover valid writes and per-item type/attribute errors, but do not
  establish parity for that exact connector request.

### B. Boiler `Switch` method returns `BadTooManyArguments`
- **Scenario:** call the Boiler `Switch` method with the input arguments advertised in its
  `InputArguments` property.
- **Observed (preview.1):** `BadTooManyArguments`. The method declaration and the method
  handler appear to disagree on the argument count.
- **Status:** fixed locally. `BoilerSwitch_AcceptsAdvertisedBooleanArgument` verifies both boolean
  values against the current model metadata.

### C. Boiler type-based discovery changed
- **Scenario:** discover asset instances by browsing for instances of `Boiler2Type`
  (`HasTypeDefinition`) and reading their component structure.
- **Observed (preview.1):** a different node set than on 2.15.x (different instances,
  components, or browse names).
- **Status:** fixed locally. `BoilerInstance_PreservesTypeDefinition` verifies the instance type,
  subtype relationship, browse name, and presence in the expected parent browse.

### D. Unknown browse path status (no action needed)
`TranslateBrowsePathsToNodeIds` with a non-existent path returns `BadNodeIdInvalid`, where
2.15.x returned `BadNoMatch`. Both are acceptable under Part 4, 5.8.4, so the connector tests
now accept either. A CHANGELOG note would still help other clients.

### E. Connector-side GDS issues (FYI)
These are caused by the connector's GDS manager, not the PLC:
- **Rollover resume:** the connector pushed the certificate before the new issuer. This now
  correctly fails with `BadCertificateChainIncomplete` (see item 1).
- **Forced CA renew:** the same ordering problem, plus connector-side reconciliation timing.

## Acceptance checks for the next preview
1. GDS push of a new certificate (trust list, then `UpdateCertificate`, then `ApplyChanges`)
   works, and the server presents the new certificate after reconnect.
2. `CreateSigningRequest` (`regeneratePrivateKey = true`) succeeds under the default Helm
   chart RBAC, and `UpdateCertificate` with the signed certificate completes.
3. CSR creation and certificate activation update only the existing own-certificate Secret, preserving
   its active identity until activation; no separately named pending Secret is created. SubPath mixed
   write returns the same per-item statuses as 2.15.x, or the difference is documented.
4. Boiler `Switch` accepts its advertised input arguments.
5. `Boiler2Type` instance discovery matches 2.15.x, or the difference is documented.

## Repro outline
1. Deploy the PLC with Helm chart `1.2.25` and the image `2.16.0-preview.4`, with GDS push
   enabled (`--gds` / the chart's GDS settings) and Kubernetes secret-backed stores.
2. From any OPC UA client with the `SecurityAdmin` role:
   - Call `CreateSigningRequest` on the default application certificate group.
   - Check the server log and the Kubernetes API audit log for the 403 on `secrets` `create`.
3. For A–C, run the equivalent Write, Call, and Browse requests against 2.15.11 and
   2.16.0-preview.4, then compare the per-item status codes and browse results.
